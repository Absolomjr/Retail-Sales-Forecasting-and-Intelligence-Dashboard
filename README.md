# Retail Sales Forecasting & Intelligence Dashboard

Predict how many units a specific product will sell in a specific store over the next **28 days**,
and put the answer — plus the analytics behind it — in front of someone who has to make a stocking
decision.

Built on the **M5 / Walmart** dataset: 3,049 products × 10 stores × 3 states, daily unit sales from
2011-01-29 to 2016-05-22 (1,941 days, 59M observations).

## Results

The model is a **direct** 28-day forecaster: every feature it uses is knowable 28 days in advance, so
the backtest score is one you could actually achieve in production.

| Model | MAE | RMSE | WMAPE | Notes |
|---|---|---|---|---|
| Naive (last value) | 1.439 | 3.123 | 96.0% | hold yesterday flat for 28 days |
| Seasonal naive (lag 28) | 1.363 | 3.196 | 91.0% | same weekday, four weeks ago |
| Linear Regression | 1.137 | 2.527 | 75.9% | one-hot + scaled, 1M-row subsample |
| Random Forest | 1.140 | 2.483 | 76.1% | 80 trees, depth 16 |
| XGBoost | 1.135 | 2.475 | 75.8% | `hist`, early-stopped |
| **LightGBM** | **1.100** | **2.440** | **73.4%** | native categoricals |
| LightGBM (Optuna-tuned) | see notebook | | | 10-trial TPE search |

Scored on a 28-day window (2016-04-25 → 05-22) never used for training or tuning, and confirmed across
four rolling-origin folds. Metrics live in `artifacts/model_metadata.json` and in MLflow.

## Key findings from the EDA

* **Weekends drive everything.** +30.9% vs weekdays — the largest effect in the data by far.
* **Christmas is a store closure, not a peak.** ~15 units chain-wide on 25 December; only 23 December
  lifts (+7.5%), and November is the weakest month of the year.
* **FOODS is 68.6% of units but 58.0% of revenue** — the cheapest category (\$3.25 average).
* **CA_3 is the strongest store** (11.4M units, \$32.7M), 2.7× the weakest.
* **Demand is inelastic** — within-series elasticity ≈ **−0.64**.
* **Promotions work unevenly**: HOBBIES +64%, FOODS +45%, HOUSEHOLD **+1.6%**.
* **SNAP days lift sales** +7.5% (CA), +11.1% (TX), +21.3% (WI).

## Two things this project is careful about

**Data leakage.** Rolling features use `.shift(1)` so today's sales never enter today's features. More
subtly, a 28-day horizon makes even `lag_1` illegal — it would not exist at prediction time. The
notebook builds both feature sets, ships the horizon-safe one, and **measures** what the leaky one
would have flattered the score by (§5.7), then shows recursive forecasting compounding that error away
(§6.5).

**Training/serving skew.** Features are built by one module, `forecasting/features.py`, imported by the
notebook and the API alike. Before the model is saved, §6.8 rebuilds the test window through the
serving path and asserts all 25 features match training exactly. If they diverge, the notebook fails.

## Running it

### 1. Get the data

Download the [M5 competition data](https://www.kaggle.com/competitions/m5-forecasting-accuracy/data)
and put `calendar.csv`, `sell_prices.csv` and `sales_train_evaluation.csv` in this folder.

### 2. Run the notebook

```bash
python -m venv .venv && .venv/Scripts/activate      # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
jupyter lab retail_forecasting.ipynb
```

Run all cells. Takes roughly 25 minutes and needs ~4 GB of RAM. It writes `artifacts/` (the model plus
its serving data) and `mlflow.db` (the experiment log).

> **Memory note.** The long-format panel is 59M rows. The notebook builds it in NumPy with explicit
> dtypes (~600 MB); the obvious `sales.melt(...)` raises `MemoryError` on an 8 GB machine. Modelling
> runs on a stratified 400-item sample — raise `N_ITEMS_SAMPLE` and lower `FIRST_DAY` in §2 if you
> have more RAM.

### 3. Start the stack

```bash
docker compose up --build
```

| Service | URL |
|---|---|
| Dashboard | http://localhost:3000 |
| API docs | http://localhost:8000/docs |
| MLflow | http://localhost:5000 |

Optionally mirror the analytics tables into Postgres:

```bash
docker compose run --rm seed
```

### Without Docker

```bash
# API  (http://localhost:8000)
cd backend && uvicorn app.main:app --reload

# dashboard (http://localhost:5173, proxies /api to localhost:8000)
cd frontend && npm install && npm run dev
```

Both commands work as written on Windows, macOS and Linux. The API adds the
repository root to `sys.path` itself, so `forecasting` — the feature module it
shares with the notebook — is importable without a `PYTHONPATH` prefix. Running
`uvicorn backend.app.main:app --reload` from the repository root works too.

Point the dashboard at an API on another port with
`VITE_API_TARGET=http://localhost:8010 npm run dev`.

Run the tests from the repository root:

```bash
pytest
```

## API

| Method | Endpoint | Returns |
|---|---|---|
| `GET` | `/api/products` | items the model can forecast (`cat_id`, `search`, `limit`) |
| `GET` | `/api/stores` | stores with lifetime units, revenue and their 28-day forecast |
| `GET` | `/api/categories` | categories with unit and revenue shares |
| `GET` | `/api/sales/history` | chain-wide daily units, or one series with `item_id`+`store_id` |
| `POST` | `/api/forecast` | live 28-day forecast for one series |
| `POST` | `/api/forecast/batch` | pre-computed forecasts for many series |
| `GET` | `/api/forecast/totals` | chain-wide daily forecast |
| `GET` | `/api/metrics` | hold-out MAE / RMSE / WMAPE / WRMSSE |
| `GET` | `/api/model/info` | model type, training window, features, hyper-parameters |
| `GET` | `/api/analytics/overview` | dashboard KPIs |
| `GET` | `/api/analytics/top-products` | best sellers by revenue |
| `GET` | `/api/analytics/weekday` | average units by day of week |
| `GET` | `/api/insights/attention` | products with declining expected demand |
| `GET` | `/api/insights/restock` | products with growing expected demand |
| `GET` | `/health` | readiness, including whether the model loaded |

**Example**

```bash
curl -X POST http://localhost:8000/api/forecast \
  -H 'Content-Type: application/json' \
  -d '{"store_id": "CA_1", "item_id": "FOODS_3_090", "horizon": 28}'
```

```json
{
  "store_id": "CA_1",
  "item_id": "FOODS_3_090",
  "horizon": 28,
  "generated_from": "2016-05-22",
  "total_predicted_units": 3021.4,
  "total_expected_revenue": 5891.73,
  "forecast": [
    { "date": "2016-05-23", "predicted_sales": 96, "sell_price": 1.95, "expected_revenue": 187.2 }
  ]
}
```

The API serves only the product-store series the model was trained on. `GET /api/products` is the
authoritative list; anything else returns `404` with an explanation rather than a fabricated number.

| Part | Contents |

| 1–2 | Load, dtype strategy, wide→long reshape, weekly price table |

| **Part 3** | Chronological train / validation / test split on the M5's 28-day horizon |
